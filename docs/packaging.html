Packaging

One command turns your app folder into an executable carrying your name, your icon and your interface — with nothing beside it.

The configuration

Create a config folder next to Proton.exe, holding a config.json and — optionally — an icon.ico: 

MyApp/
├── Proton.exe
├── app/
└── config/
    ├── config.json
    └── icon.ico

Two properties are required. Everything else has a sensible default:

{
  "name": "Inventory Manager",
  "executableName": "InventoryManager"
}
PropertyMeaningDefault
name The application's name, returned by /api/app and written into the file's Windows properties required
executableName The file to produce. .exe is added if you leave it off required
windowTitle The window's title bar falls back to name
version Shown in the file's properties, and on /api/app none
company Same none
window.width Window width in pixels 1280
window.height Window height in pixels 800
window.resizable Whether the user may resize it true

A complete one:

{
  "name": "Inventory Manager",
  "executableName": "InventoryManager",
  "windowTitle": "Inventory Manager — 2026 Edition",
  "version": "2.4.1",
  "company": "Kevin's Workshop",
  "window": { "width": 1280, "height": 800, "resizable": true }
}

icon.ico becomes the file's icon, the taskbar icon and the window icon. Provide several resolutions in the one .ico and Windows picks what it needs. Without it, the generated executable keeps Proton's icon.

Generating

Proton.exe /generate

You get InventoryManager.exe: the same engine, carrying your metadata and your application inside it. Proton.exe is left untouched — an executable never modifies itself, so you can generate as many applications from it as you like.

Run it from a command prompt and the report goes to the console. Launch it by double-clicking and the same report appears in a dialog, since there is no console to write to. The exit code is 0 on success and 2 on failure.

--generate works too, for shells that rewrite arguments beginning with a slash — Git Bash turns /generate into a Windows path. /config, the spelling used in 1.0, is still accepted.

Your application is never unpacked onto the disk. It is served from within the executable, so a new version of your program always ships the interface that belongs to it. The two cannot drift apart, and there is no app folder for a user to edit by accident.

What the executable produces on first run

Anywhere/
├── InventoryManager.exe
└── data/
    ├── files/
    └── db/

That is all. No app, no config — those belong to development, not to distribution.

Shipping initial content

To deliver templates, a catalogue or a pre-filled database, put them in data and add the data argument: 

Proton.exe /generate data

Both data/files and data/db are embedded, and laid down on first run — but only if data does not already exist.

It is all or nothing, deliberately. Once a user has started using the application, that folder is theirs; mixing delivered content into it would produce a state nobody could reason about afterwards.

Distributing

Copy the single file. Another folder, a USB stick, a network share, another machine — nothing travels with it.

SizeAround 63 MB — the .NET runtime is inside, compressed
Requires64-bit Windows 10 or 11, with Microsoft Edge WebView2
InstallsNothing. It writes only its own data folder
UninstallsDelete the file and its folder

WebView2 ships with Windows 11 and with recent Windows 10 installs. If it is missing, Proton says so in a dialog rather than failing silently.

Licence and attribution

Proton is MIT. Applications you build with it are yours: ship them however you like, commercially or not, with no obligation to publish your source.

The engine is embedded in every executable produced, so the attribution MIT asks for is written there automatically — in the file's Windows properties and on /api/app. There is nothing for you to do.

When it fails

MessageCause
"…\app" was not found. No app folder beside the executable — there is nothing to embed
"…\config\config.json" was not found. No configuration to read
"name" and "executableName" are required. One of the two required properties is missing or empty
config.json could not be read: … The JSON is malformed — the parser says where
The target is the source executable… executableName names Proton.exe itself
"…" could not be replaced. Is the application still running? A previous build of the target is still open

Nothing is written until the final line. Proton builds the file under a temporary name, verifies that its bundle is intact and that the embedded configuration reads back, and only then moves it into place. A failed generation leaves no half-written executable behind.
